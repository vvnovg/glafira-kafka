# Kafka Explorer — спецификация

**Дата:** 2026-10-14
**Статус:** черновик на ревью
**Тип:** desktop-приложение (Tauri 2 + Rust + React/TypeScript)

---

## 1. Цель и аудитория

Kafka Explorer — кроссплатформенное desktop-приложение для интерактивной работы с Kafka-кластерами. Оно заменяет связку `kafka-topics.sh` / `kafka-console-consumer` / `kcat` / самописных скриптов единым GUI.

**Пользователи:**
- **Тестировщики** — отправляют тестовые сообщения, ищут нужное сообщение в топике, проверяют, что сервис что-то записал или прочитал, сбрасывают оффсеты перед прогоном.
- **Разработчики** — отлаживают продюсеры и консьюмеры, смотрят лаг, создают и настраивают топики на dev/test-стендах, декодируют Avro/Protobuf.

**Ключевые сценарии (критерии успеха MVP):**
1. Подключиться к кластеру с любой из поддерживаемых схем аутентификации меньше чем за минуту (включая импорт сертификатов).
2. Найти сообщение в топике по подстроке в ключе, значении или заголовке, с ограничением по времени или оффсету.
3. Отправить сообщение (в том числе Avro/Protobuf через Schema Registry) с ключом и заголовками; отправить пачку сгенерированных сообщений.
4. Прочитать топик как участник consumer group: увидеть назначение партиций и ребалансы, закоммитить оффсеты вручную.
5. Создать топик, изменить его конфигурацию, добавить партиции, очистить или удалить его.
6. Посмотреть consumer groups, их лаг по партициям и сбросить оффсеты.

**Не-цели MVP:** управление ACL, Kafka Connect, ksqlDB, квоты, мониторинг и метрики во времени (графики), реассайнмент партиций, многопользовательский или серверный режим.

## 2. Ключевые технические решения

| Решение | Выбор | Причина |
|---|---|---|
| Оболочка | **Tauri 2** | Лёгкий бинарник (~15–25 МБ с librdkafka), нативный WebView, безопасная IPC-модель |
| Kafka-клиент | **rust-rdkafka** (librdkafka, статическая сборка `cmake-build`) | Полная поддержка SSL/mTLS, SASL PLAIN/SCRAM/GSSAPI/OAUTHBEARER, Admin API |
| UI | **React 18 + TypeScript + Vite**, TanStack Query/Table/Virtual, Zustand, Monaco Editor | Виртуализированные таблицы для больших списков, редактор JSON/Avro/Proto с подсветкой |
| Schema Registry | Свой HTTP-клиент на `reqwest`; `apache-avro`, `prost-reflect` + `protox`, `jsonschema` | Совместимость с Confluent wire format без JVM |
| Хранилище настроек | JSON-файлы в app data dir | Простота, переносимость, читаемость |
| Секреты | OS keychain через крейт `keyring` (macOS Keychain, Windows Credential Manager, Secret Service) | Пароли и ключи не лежат на диске в открытом виде |
| Платформы | macOS (arm64, x64), Windows x64, Linux x64 (AppImage, deb) | |
| Поддерживаемые версии Kafka | 2.8+ (ZooKeeper и KRaft), Redpanda, AWS MSK, Confluent Cloud | |

## 3. Архитектура

```
┌───────────────────────── WebView (React) ──────────────────────────┐
│  Sidebar (дерево)  │  Вкладки рабочей области  │  Command palette   │
│  api/ — типизированные обёртки над invoke() и Channel               │
└───────────────▲──────────────────────────────┬─────────────────────┘
                │ Tauri events / Channel        │ invoke(command)
┌───────────────┴──────────── Rust core ───────▼─────────────────────┐
│ commands/      — тонкий слой IPC, валидация, маппинг ошибок         │
│ connections/   — профили, сборка ClientConfig, пул клиентов         │
│ auth/          — SSL/сертификаты, SASL, OAuth/MSK IAM токены        │
│ admin/         — топики, конфиги, брокеры, группы (AdminClient)     │
│ browse/        — чтение без группы (assign), фильтры, буфер         │
│ consume/       — consumer-сессии с group.id                         │
│ produce/       — отправка, шаблоны, генерация пачек                 │
│ serde/         — форматы: string/json/bytes/avro/protobuf/jsonschema│
│ schema_registry/ — клиент SR, кэш схем                              │
│ storage/       — профили, шаблоны, история, настройки              │
│ secrets/       — keychain                                           │
└─────────────────────────────────────────────────────────────────────┘
```

### 3.1 Принципы
- **Вся работа с Kafka — в Rust.** Фронтенд не знает о librdkafka; он вызывает команды и получает потоки данных.
- **Каждый модуль тестируется изолированно:** `admin`, `browse`, `consume`, `produce` зависят от трейта `KafkaClients` (фабрика клиентов по `ConnectionId`), а `serde` — от трейта `SchemaSource`. Это позволяет подменять их в тестах.
- **Длительные операции** (browse, consumer-сессии, пакетная отправка) — это фоновые tokio-задачи с `SessionId`. Данные идут во фронтенд через `tauri::ipc::Channel` батчами (до 200 сообщений или раз в 100 мс). Отмена — командой `stop_session(id)` через `CancellationToken`.
- **Пул клиентов:** на одно подключение — один `AdminClient` и один `BaseProducer`, они создаются лениво и переиспользуются. Consumer'ы создаются отдельно на каждую сессию. При закрытии подключения всё уничтожается.

### 3.2 IPC-контракт (основные команды)

| Группа | Команды |
|---|---|
| Подключения | `list_connections`, `save_connection`, `delete_connection`, `test_connection`, `connect`, `disconnect`, `import_connections`, `export_connections` |
| Кластер | `get_cluster_overview`, `list_brokers`, `get_broker_config` |
| Топики | `list_topics`, `get_topic`, `get_topic_configs`, `create_topic`, `alter_topic_configs`, `add_partitions`, `delete_topics`, `purge_topic` |
| Группы | `list_groups`, `get_group`, `preview_offset_reset`, `reset_offsets`, `delete_group` |
| Browse | `start_browse(params, channel) -> SessionId`, `stop_session` |
| Consume | `start_consumer(params, channel) -> SessionId`, `commit_offsets`, `pause_partitions`, `resume_partitions`, `stop_session` |
| Produce | `produce(message)`, `produce_batch(params, channel) -> SessionId`, `list_templates`, `save_template`, `delete_template` |
| Schema Registry | `sr_list_subjects`, `sr_get_versions`, `sr_get_schema`, `sr_get_compatibility` |
| Прочее | `export_messages`, `get_settings`, `save_settings` |

Все команды возвращают `Result<T, AppError>`, где `AppError` — сериализуемый enum с полями `code`, `message`, `details` (см. §8).

## 4. Функциональные требования

### 4.1 Подключения

**Профиль подключения:**
- имя, цвет, **окружение** (`local` / `dev` / `test` / `stage` / `prod`), флаг **read-only**;
- `bootstrap.servers`;
- протокол безопасности и параметры аутентификации (см. ниже);
- Schema Registry: URL и аутентификация (none / basic / bearer / mTLS);
- дополнительные свойства librdkafka (key-value, «для продвинутых»);
- таймауты: запрос (по умолчанию 30 с), подключение (10 с).

**Поддерживаемые схемы аутентификации:**

| Схема | Параметры | Реализация |
|---|---|---|
| PLAINTEXT | — | |
| SSL (TLS) | CA-сертификат (или системное хранилище), проверка hostname (вкл./выкл.) | `ssl.ca.location` / `ssl.ca.pem` |
| SSL с клиентским сертификатом (mTLS) | Клиентский сертификат + ключ + пароль ключа. Форматы: **PEM**, **PKCS#12 (.p12/.pfx)**, **JKS** | PEM — напрямую, PKCS#12 — через `ssl.keystore.location`, JKS — **конвертация в PEM при импорте** (парсер JKS в Rust) |
| SASL PLAIN | логин/пароль, поверх PLAINTEXT или SSL | |
| SASL SCRAM-SHA-256/512 | логин/пароль | |
| SASL GSSAPI (Kerberos) | principal, keytab или kinit-кэш, service name | librdkafka с feature `gssapi` (macOS/Linux — системный krb5, Windows — SSPI) |
| SASL OAUTHBEARER (OIDC) | token endpoint, client id/secret, scope, extensions | Встроенный OIDC librdkafka (`sasl.oauthbearer.method=oidc`) |
| AWS MSK IAM | регион; источник учётных данных: профиль `~/.aws`, env, явные ключи, assume role | OAUTHBEARER + callback `generate_oauth_token`, который генерирует SigV4-токен (порт логики `aws-msk-iam-sasl-signer`, `aws-sdk` для credentials) |

**Сертификаты:**
- Импорт файлов копирует их в каталог приложения (`certs/<connection-id>/`). Пароли keystore и ключей хранятся в keychain.
- В UI показываются subject, issuer и срок действия сертификата. Если до истечения меньше 30 дней или срок уже истёк — показывается предупреждение.

**Операции:**
- **Test connection** — проверяет по шагам, что именно удалось: DNS/TCP → TLS handshake → SASL → metadata → Schema Registry. Ошибка показывается на конкретном шаге с подсказкой (например, «hostname не совпадает с CN/SAN сертификата»).
- Экспорт/импорт профилей в JSON **без секретов**: секреты заменяются плейсхолдерами, при импорте их запрашивают у пользователя.
- Одновременно можно открыть несколько подключений, каждое — отдельный узел в дереве.

**Хранение:** `connections.json` (без секретов), секреты — в keychain под ключом `kafka-explorer/<connection-id>/<field>`.

### 4.2 Обзор кластера
- Cluster ID, контроллер, режим (KRaft/ZK, если удаётся определить), список брокеров (id, host:port, rack).
- Счётчики: топики, партиции, under-replicated и offline-партиции (подсвечиваются).
- Конфигурация брокера (только чтение) с источником каждого значения (default / static / dynamic).

### 4.3 Топики

**Список:**
- Виртуализированная таблица, рассчитанная на 10 000+ топиков: имя, партиции, RF, примерное число сообщений (Σ(high − low watermark)), размер на диске (через `DescribeLogDirs`, если есть права), cleanup.policy.
- Поиск по подстроке и regex; переключатель «показывать внутренние» (`__consumer_offsets`, `_schemas` и т. п.); избранные топики (закрепляются наверху, хранятся в настройках по каждому подключению).
- Ручное обновление и автообновление (выкл. / 10 с / 30 с).

**Детали топика** (вкладка с подвкладками):
- **Messages** — browse (§4.5);
- **Partitions** — leader, replicas, ISR, low/high watermark, количество сообщений; under-replicated подсвечиваются;
- **Configs** — все параметры: значение, значение по умолчанию, источник, флаг sensitive/read-only. Изменённые относительно default параметры выделяются;
- **Consumer groups** — группы, у которых есть коммиты в этот топик, и их лаг;
- **Schema** — связанные subjects `<topic>-key` и `<topic>-value`, если настроен Schema Registry.

**Операции** (недоступны в read-only):
- **Создать топик:** имя (с валидацией по правилам Kafka), партиции, RF (подсказка — число брокеров), пресеты (`delete`, `compact`, `compact+delete`, короткий retention для тестов), произвольные конфиги, предпросмотр итоговой команды `kafka-topics.sh` для справки.
- **Изменить конфиги:** через `IncrementalAlterConfigs`; редактор показывает diff «было → стало» перед применением; есть сброс к default (`DELETE`).
- **Добавить партиции:** только увеличение числа, с предупреждением о нарушении порядка сообщений по ключам.
- **Очистить (purge):** `DeleteRecords` до high watermark по всем или выбранным партициям. Для `compact`-топиков показывается предупреждение.
- **Удалить:** подтверждение вводом имени топика; можно удалить несколько топиков сразу.

### 4.4 Consumer groups

**Список:** group id, состояние (Stable, Empty, PreparingRebalance, Dead…), протокол / assignor, число участников, суммарный лаг, топики. Поиск и фильтр по состоянию.

**Детали группы:**
- таблица по партициям: топик, партиция, committed offset, log end offset, lag, участник (client id, host);
- участники и их назначения;
- автообновление лага (5 с / 10 с / выкл.).

**Сброс оффсетов** (только для группы в состоянии `Empty`, иначе ошибка с объяснением):
- стратегии: `earliest`, `latest`, `timestamp` (через `offsetsForTimes`), конкретный оффсет, сдвиг на ±N;
- область: вся группа / выбранные топики / выбранные партиции;
- **обязательный предпросмотр** (dry-run): таблица «текущий → новый» по каждой партиции, затем кнопка «Применить».

**Удаление группы** — только `Empty`, с подтверждением.

### 4.5 Просмотр сообщений (Browse)

Режим «посмотреть, не влияя на кластер»: consumer **без group.id**, партиции назначаются через `assign`, коммитов нет.

**Параметры запуска:**
- партиции: все или выбранные;
- начальная позиция: `latest N` (по умолчанию 100 на всю выборку, распределяется по партициям), `earliest`, оффсет, timestamp (дата-время с часовым поясом), «последние X минут»;
- лимит: N сообщений (по умолчанию 500, максимум 100 000) или «до текущего конца»;
- **Live tail:** после достижения конца продолжать получать новые сообщения;
- формат ключа и значения: `auto` (по умолчанию), `string`, `json`, `bytes (hex)`, `base64`, `avro (SR)`, `protobuf (SR)`, `json schema (SR)`, `protobuf (локальный .proto)`, int/long/double (big-endian);
- **фильтры** (применяются в Rust до отправки в UI): подстрока или regex по ключу, значению, заголовку (имя = значение); JSONPath-условие по значению (`$.order.status == "FAILED"`); диапазон времени. Есть счётчик «просмотрено / найдено».

**Auto-детект формата:** magic byte `0x00` + 4 байта schema id → декодирование через SR; иначе валидный UTF-8 JSON → json; иначе UTF-8 → string; иначе → hex.

**Отображение:**
- виртуализированная таблица: partition, offset, timestamp (локальное время / UTC — переключатель), key, превью value, число заголовков, размер. Сортировка — по timestamp или по offset внутри партиции;
- панель деталей: значение в Monaco (pretty JSON, свёртка), hex-view, заголовки, метаданные (schema id, subject, version, compression, timestamp type);
- действия с сообщением: копировать key/value/всё как JSON; **«Отправить повторно»** — открывает Producer с предзаполненными полями; **«Сбросить группу сюда»** — переход к сбросу оффсетов на этот оффсет.

**Экспорт:** выбранные или все загруженные сообщения в JSON Lines / CSV, с заголовками и метаданными.

**Ограничения памяти:** буфер в UI — не больше 100 000 сообщений (кольцевой буфер в режиме live tail). Значения больше 1 МБ в таблице обрезаются в превью и загружаются целиком по запросу.

### 4.6 Producer

**Одиночная отправка:**
- топик (автодополнение), партиция (`auto` или конкретная), key, value, headers (список key-value; значения — string или hex);
- формат key/value — как в §4.5. Для SR-форматов выбирается subject и версия (по умолчанию `TopicNameStrategy`, latest); значение вводится как JSON и **валидируется по схеме** до отправки;
- параметры продюсера: `acks` (0/1/all), compression, idempotence;
- результат: partition, offset, timestamp или понятная ошибка.

**Шаблоны:** сохранить текущую форму как именованный шаблон (на уровне подключения или глобально). В шаблонах есть **плейсхолдеры:** `{{uuid}}`, `{{now}}` (ISO), `{{nowMillis}}`, `{{seq}}`, `{{randomInt min max}}`, `{{randomString n}}`, `{{env NAME}}`.

**Пакетная отправка:**
- N копий шаблона с подстановкой плейсхолдеров, с ограничением скорости (сообщ./с) или без;
- импорт из файла JSON Lines (`{"key":…, "value":…, "headers":{…}, "partition":…}`) или CSV;
- прогресс, отправлено / ошибки, отмена.

**История:** последние 100 отправленных сообщений по каждому подключению (без секретов), с повтором в один клик.

### 4.7 Consumer-сессии (чтение как участник группы)

Отличие от Browse — **влияет на кластер:** присоединяется к group, участвует в ребалансе, коммитит оффсеты. Перед запуском показывается баннер с предупреждением.

**Параметры:** group.id (вручную или сгенерированный `kafka-explorer-<user>-<short-uuid>`), топики (список или regex-подписка), `auto.offset.reset`, `enable.auto.commit` (по умолчанию **выкл.**), `isolation.level`, форматы и фильтры как в Browse.

**Во время сессии:**
- поток сообщений (та же таблица, что в Browse);
- панель **Assignment:** текущие партиции и журнал событий ребаланса (assigned / revoked с временем);
- **ручной коммит:** «закоммитить до выбранного сообщения» или «закоммитить всё прочитанное»;
- pause/resume по партициям;
- остановка: `close()` с корректным выходом из группы.

Можно запустить несколько сессий параллельно, каждая — в своей вкладке. Это полезно для проверки ребаланса (две сессии в одной группе).

### 4.8 Schema Registry
- Список subjects с поиском, версии subject, просмотр схемы (Avro / Protobuf / JSON Schema) с подсветкой, уровень совместимости (subject / глобальный).
- Кэш схем по id на время жизни подключения.
- Protobuf: поддержка message indexes из wire format и импортов (references) из SR.
- Локальные `.proto`-файлы как альтернативный источник схем для топиков без SR: привязка «топик → файл + message type» в настройках подключения.
- **Вне MVP:** регистрация и удаление схем, изменение совместимости.

### 4.9 Интерфейс

- **Раскладка:** слева дерево (Подключения → Topics / Consumer Groups / Schemas / Brokers), справа рабочая область с вкладками (вкладки переставляются, закрываются, восстанавливаются после перезапуска).
- **Индикация окружения:** цветная полоса вверху рабочей области и бейдж в табе (`PROD` — красный). Для read-only — значок замка; кнопки изменения скрыты.
- **Command palette** (`Cmd/Ctrl+K`): переход к топику, группе, подключению, действию.
- **Горячие клавиши:** новая вкладка Producer (`Cmd+Shift+P`), обновить (`Cmd+R`), закрыть вкладку (`Cmd+W`), поиск в таблице (`Cmd+F`).
- Тёмная и светлая тема (по системной), локализация **ru / en** (i18next).
- Пустые состояния и подсказки при первом запуске («Добавьте первое подключение», пример docker-compose для локальной Kafka).

## 5. Безопасность

- **Read-only профили:** блокировка всех мутирующих команд **на уровне Rust** (не только в UI): create/alter/delete topic, purge, reset/delete group, produce, consumer-сессии с коммитом.
- **Окружение `prod`:** по умолчанию read-only при создании профиля. Если read-only снят, каждая мутирующая операция требует подтверждения вводом имени подключения.
- Удаление топика или группы и purge — всегда с подтверждением вводом имени.
- Секреты — только в keychain; в логах и экспорте маскируются (`****`).
- CSP в WebView, Tauri capabilities разрешают только собственные команды. Нет удалённого контента, **нет телеметрии**.
- Логи приложения (`tracing`, ротация, 7 дней) — в app data dir, с кнопкой «Открыть папку логов» для баг-репортов.

## 6. Нефункциональные требования

| Метрика | Цель |
|---|---|
| Холодный старт | < 2 с |
| Список 10 000 топиков | загрузка метаданных < 3 с, плавный скролл (60 fps) |
| Browse | ≥ 5 000 сообщ./с в UI без фризов (≤ 1 КБ на сообщение) |
| Память | < 500 МБ при 100 000 сообщений в буфере |
| Размер установщика | < 40 МБ |
| Таймауты | ни одна операция не блокирует UI; у всех сетевых операций есть таймаут и отмена |

## 7. Модель данных (хранилище)

```
<app_data>/
  connections.json      # [{id, name, color, env, readOnly, bootstrap, security:{...без секретов}, schemaRegistry:{...}, extraProps, favorites:[...]}]
  templates.json        # [{id, name, connectionId|null, topic, partition, key, value, headers, formats}]
  history/<conn-id>.json# последние 100 отправленных
  settings.json         # тема, язык, timezone, лимиты по умолчанию, открытые вкладки
  certs/<conn-id>/...   # импортированные сертификаты
  logs/
```

Файлы версионируются полем `schemaVersion` и мигрируются при старте.

## 8. Обработка ошибок

`AppError { code, message, details?, retryable }`. Основные коды:

| code | Пример причины | Поведение UI |
|---|---|---|
| `CONNECTION_FAILED` | брокер недоступен, DNS | баннер с кнопкой «Повторить» |
| `TLS_ERROR` | неверный CA, hostname mismatch, истёкший сертификат | подсказка по конкретной причине |
| `AUTH_FAILED` | неверный пароль, Kerberos, просроченный токен | ссылка «Изменить подключение» |
| `NOT_AUTHORIZED` | нет прав по ACL на топик/группу/операцию | действие становится недоступным, объяснение в tooltip |
| `TIMEOUT` | операция не уложилась в таймаут | «Повторить» |
| `INVALID_INPUT` | невалидное имя топика, JSON не соответствует схеме | ошибка у поля формы |
| `GROUP_NOT_EMPTY` | сброс оффсетов в активной группе | объяснение и список активных участников |
| `SCHEMA_ERROR` | SR недоступен, схема не найдена, ошибка декодирования | сообщение показывается как raw (hex) с пометкой об ошибке, browse продолжается |
| `READ_ONLY` | мутирующая операция на read-only профиле | |
| `INTERNAL` | всё остальное | показ деталей, ссылка на логи |

**Частичные результаты:** если часть данных недоступна (например, `DescribeLogDirs` запрещён), остальное показывается, а недоступное поле помечается «—» с tooltip-причиной.

Потеря соединения во время сессии: автоматический реконнект средствами librdkafka; в UI статус сессии меняется на `reconnecting`, через 60 с без восстановления — на `failed`.

## 9. Тестирование

- **Rust unit:** `serde` (все форматы, wire format SR, auto-детект), фильтры (regex, JSONPath), плейсхолдеры шаблонов, сборка `ClientConfig` из профиля (по каждой схеме auth), JKS→PEM конвертация, генерация MSK IAM токена (по эталонным векторам), миграции хранилища.
- **Rust integration** (testcontainers, docker-compose):
  - Kafka KRaft (PLAINTEXT) + Schema Registry — полный цикл: create topic → produce (string/json/avro/protobuf) → browse с фильтрами → consumer-сессия с коммитом → reset offsets → purge → delete;
  - матрица аутентификации: SSL, mTLS (PEM/PKCS#12/JKS), SASL PLAIN, SCRAM-256/512, OAUTHBEARER (с mock OIDC — например, Keycloak), Kerberos (контейнер с KDC);
  - read-only: каждая мутирующая команда возвращает `READ_ONLY`.
- **Frontend:** Vitest + Testing Library для компонентов (формы, таблицы, редактор конфигов, предпросмотр сброса оффсетов); IPC мокается.
- **E2E:** WebdriverIO + `tauri-driver` на Linux и Windows в CI — смоук ключевых сценариев из §1.
- **Ручной чек-лист перед релизом:** AWS MSK IAM и Confluent Cloud (облачные, не в CI), подписание и нотаризация на macOS.

## 10. Сборка и дистрибуция

- GitHub Actions: матрица macOS (arm64/x64), Windows, Linux; кэш cargo и сборки librdkafka.
- librdkafka собирается статически (`cmake-build`, features `ssl`, `sasl` (gssapi), `zstd`, `libz`); на Linux — зависимость от системного `libsasl2`/krb5 описана в deb-пакете.
- Подписание: Apple Developer ID + нотаризация, Windows Authenticode (если есть сертификат).
- Автообновление: Tauri updater с подписанными релизами в GitHub Releases (проверка при старте, отключаемая).

## 11. Этапы реализации

MVP — этапы M1–M4.

| Этап | Содержимое |
|---|---|
| **M1. Каркас и чтение** | Tauri-проект, хранилище, keychain, подключения (PLAINTEXT, SSL, SASL PLAIN/SCRAM), test connection, обзор кластера, список и детали топиков, Browse (string/json/hex, фильтры, live tail) |
