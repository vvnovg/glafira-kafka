## 2. Выбор языка

Приоритет:
1. язык из корпоративной политики (`language`);
2. выбор пользователя;
3. язык ОС;
4. английский.

- Pro-язык действует только при Pro-лицензии, в том числе язык из политики.
- Если язык требует Pro, а лицензии нет (не было или истекла), действует английский. Выбор пользователя при этом не стирается, а на экране «Настройки» видна причина.
- Язык ОС сопоставляется по основному тегу: `de-AT` → `de`, `pt-PT` → `pt-BR` (ближайший доступный), `uk` → `en`.
- Смена языка применяется сразу, без перезапуска.

### 2.1 Хранение и проверки (Rust)

- `settings.json` в данных приложения: `{ "schemaVersion": 1, "language": "de" | null }`. `null` означает «как в системе». Чтение устроено так же, как у лицензии: повреждённый файл не мешает запуску (`read_json_or_quarantine`).
- `get_language_settings() -> LanguageSettings`:
  ```
  { system: "de-DE", systemMatch: "de", chosen: "de" | null, policy: "fr" | null,
    effective: "en", reason: "proRequired" | "policy" | "user" | "system" | "default", proLanguages: [...], languages: [...] }
  ```
- `set_language(lang: Option<String>)`:
  - неизвестный код → `INVALID_INPUT`;
  - Pro-язык без Pro → `PRO_REQUIRED`;
  - язык задан политикой → `INVALID_INPUT` «Язык задан вашей организацией».
- Ключ политики `language`: строка с кодом из таблицы §1. Неизвестный код записывается в `errors` политики и игнорируется. Обновления при этом не выключаются: ключ `language` к безопасности не относится.
- Язык ОС определяется в Rust: `sys_locale` или аналог.

### 2.2 Экран «Настройки»

- Ссылка «Настройки» внизу левой панели, рядом с «Лицензия» и «О программе». Вкладка `{ kind: "settings" }`.
- Раздел «Язык»:
  - список с самоназваниями языков и пунктом «Как в системе (…)»;
  - Pro-языки без лицензии видны с замком и подсказкой «Доступно в Pro», выбрать их нельзя;
  - если язык задан политикой, список недоступен с пояснением «Язык задан вашей организацией»;
  - если действует английский вместо выбранного Pro-языка, показывается причина.
- Позже сюда же переедут другие пользовательские параметры (вне этого подпроекта).

## 3. Фронтенд

- Библиотеки `i18next` и `react-i18next`. Словари — `src/locales/<code>.json`, вложенные ключи по экранам: `connections.form.name`, `topics.list.empty`, `errors.readOnly`.
- Плюрализация — встроенная в i18next через `Intl.PluralRules`. Это нужно для `ru` и `pl`: формы `_one`, `_few`, `_many`, `_other`.
- Базовый и запасной язык — `en`. Отсутствующий ключ показывается по-английски, а не именем ключа. В dev-режиме отсутствие ключа пишется в консоль.
- Форматы через `Intl` по действующему языку: `formatTimestamp`, `formatBytes`, `formatCount`, относительные времена. Сюда относятся разделители чисел и формат дат.
- Псевдоязык `x-pseudo`: появляется только в dev-сборке (`import.meta.env.DEV`). Превращает текст в `[!! Тéкст !!]`, удлиняя его примерно на 30 %, чтобы находить забытые строки и проверять ширину.
- Тесты компонентов задают язык явно: существующие тесты остаются на `ru`, новые пишутся на `en`.

### 3.1 Что не переводится

- Данные пользователя: имена топиков, групп, подключений, ключи и значения конфигов (`cleanup.policy`), заголовки сообщений.
- Термины Kafka в составе фраз определяет глоссарий: обычно не переводятся topic, partition, offset, consumer group, broker, producer, consumer, lag.
- `details` ошибок: тексты librdkafka, OpenSSL и ОС.
- Логи и архив диагностики пишутся на английском, чтобы их могла читать поддержка.

## 4. Ошибки из Rust

- `AppError` получает поля:
  - `key: String` — ключ словаря, например `errors.readOnly`;
  - `params: BTreeMap<String, String>` — подстановки, например `{ name: "prod-1" }`;
  - `message` остаётся: английский текст для логов и запасной вариант на случай, если интерфейс не знает ключа.
- Конструкторы вида `AppError::read_only(name)` или макрос `app_err!("errors.readOnly", name = …)` с английским шаблоном рядом. Код (`ErrorCode`) не меняется.
- Около 250 мест переходят на ключи, по модулям.
- `ErrorBanner` и все места, где показывается `message`, используют перевод по `key` и `params`, а при отсутствии ключа — `message`.
- Сообщения шагов проверки подключения (`TestStep.message`) переходят на ключи так же.
- Тест (Rust + скрипт): каждый `key` из исходников Rust есть в `en.json`, и параметры шаблона совпадают.

## 5. Проверки качества

- `scripts/i18n-check.mjs`, запускается в CI через `pnpm test:scripts`:
  - во всех восьми словарях одинаковое множество ключей, плюрализационные формы считаются по правилам языка;
  - в каждой строке одинаковый набор параметров `{{name}}`;
  - ключи из Rust есть в словарях;
  - вне `src/locales/` и тестов во фронтенде нет кириллицы, то есть забытых русских строк.
- Ручная проверка:
  - смоук на `en` и `ru` (все экраны);
  - для каждого Pro-языка — просмотр носителем по чек-листу экранов и проверка, что тексты не обрезаются на ширине окна 1400 px и минимальной 900 px.
