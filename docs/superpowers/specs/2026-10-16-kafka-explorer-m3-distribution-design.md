# Kafka Explorer — M3 «Готово к раздаче»: дизайн

**Дата:** 2026-10-16
**Статус:** на согласовании
**Основная спецификация:** `docs/superpowers/specs/2026-10-14-kafka-explorer-design.md`
**Предыдущие этапы:** M1, M2a, M2b (в `main`)

Документ фиксирует решения для первого распространяемого релиза: mTLS, лицензии Free/Pro, корпоративная политика, сборка и раздача установщиков. Где он молчит, действует основная спецификация.

---

## 1. Дорожная карта распространения

Продукт будут ставить тысячи человек, сначала внутри одной корпорации, потом публично. Работа разбита на независимые подпроекты. У каждого своя спека, план и ветка.

| # | Подпроект | Суть | Этап |
|---|---|---|---|
| A | mTLS | клиентские сертификаты PEM / PKCS#12 / JKS | **M3 (этот документ)** |
| E | Релиз | установщики, CI, автообновление, политика, диагностика | **M3** |
| F₁ | Лицензии без оплаты | офлайн-ключи, границы Free/Pro, утилита выдачи | **M3** |
| B | Локализация | словари во фронтенде; ошибки Rust переходят на коды и параметры | следующий |
| C | Контекстная помощь | подсказка у каждой кнопки и поля, ссылки «подробнее» | после B |
| D | Документация | руководство пользователя на нескольких языках | после C |
| F₂ | Оплата | сервис-продавец (Paddle, Lemon Squeezy и т. п.), автоматическая выдача ключей | по спросу |
| — | Остальное из M4, Schema Registry | Pro-функции | позже |

M3 даёт бету: её можно раздать в корпорации и собрать отзывы до большой работы над текстами (B–D).

## 2. Модель Free / Pro

Код закрытый. Один бинарник; Pro-функции включаются лицензионным ключом. Установщики бесплатно скачиваются из публичного репозитория релизов.

| Функция | Free | Pro |
|---|---|---|
| Просмотр кластера, топиков, групп и сообщений, фильтры | ✓ | ✓ |
| Создание, изменение, очистка и удаление топиков, сброс оффсетов | ✓ | ✓ |
| Producer: одиночная и пакетная отправка, шаблоны, история, «Отправить повторно» | ✓ | ✓ |
| Подключения PLAINTEXT, SSL, **mTLS**, SASL PLAIN/SCRAM | ✓ | ✓ |
| Флаг «только чтение»; ввод имени объекта при удалении и очистке | ✓ | ✓ |
| **Consumer-сессии** (чтение как член группы, коммит, pause/resume) | — | ✓ |
| **Режим prod**: окружение `prod`, ввод имени подключения на любое изменение, в будущем политики | — | ✓ |
| Языки, кроме английского (после B) | — | ✓ |
| M4 и дальше: Schema Registry, экспорт, command palette, Kerberos, OAuth, MSK IAM… | — | ✓ |

- Pro-элементы в Free **видны**: они неактивны, рядом замок и подсказка «Доступно в Pro» со ссылкой на экран «Лицензия».
- **Понижение тарифа не ослабляет безопасность.** Существующие профили с окружением `prod` сохраняют подтверждения и без лицензии. Без лицензии нельзя создать новый prod-профиль или переключить профиль в `prod`.
- На время беты Pro-ключи выдаются бесплатно. Оплата появится в подпроекте F₂.

## 3. Блок 1 — mTLS

### 3.1 Модель

`TlsConfig` (профиль подключения) расширяется:

```
TlsConfig {
  caLocation: string | null           // как в M1: PEM-путь; пусто → системные CA ("probe")
  caFormat: "pem" | "pkcs12" | "jks"  // новый; по умолчанию "pem"
  verifyHostname: bool
  clientCert: null | {
    format: "pem" | "pkcs12" | "jks"
    certificatePath: string           // PEM: сертификат (цепочка); PKCS#12/JKS: хранилище
    keyPath: string | null            // только для PEM
    alias: string | null              // только для JKS, если записей с ключом несколько
  }
}
```

Пароли хранятся в системном хранилище секретов (как пароль SASL):
- `ssl.key.password` — пароль ключа (PEM с зашифрованным ключом; ключ в JKS);
- `ssl.keystore.password` — пароль хранилища PKCS#12/JKS клиента;
- `ssl.truststore.password` — пароль хранилища CA в формате PKCS#12/JKS.

**Все пароли необязательны.** Незашифрованный PEM — основной сценарий: `tls.crt` / `tls.key` / `ca.crt` из секрета Kubernetes, сертификаты Istio и cert-manager. Пустой пароль PKCS#12 допустим. Для JKS без пароля проверка целостности хранилища пропускается, а пароль ключа берётся пустым или равным паролю хранилища, как в Java.

Старые профили (без `caFormat` и `clientCert`) читаются без миграции схемы: новые поля имеют значения по умолчанию.

### 3.2 Подключение

`build_client_config` при каждом создании клиента:
1. читает файлы по путям из профиля (после ротации сертификата подхватывается новый файл);
2. переводит PKCS#12 и JKS в PEM **в памяти**;
3. передаёт результат в librdkafka через `ssl.certificate.pem`, `ssl.key.pem`, `ssl.ca.pem`. Временных файлов нет.

Разбор PKCS#12 и JKS живёт в отдельном модуле `src-tauri/src/tls/`. Библиотеки выбираются в плане. OpenSSL уже входит в сборку (vendored) и разбирает PKCS#12; для JKS нужен парсер, сторонний или свой: формат простой, ключи защищены схемой Sun на SHA-1.

Чтение файлов и разбор выполняются в `commands::blocking`, как и прочая блокирующая работа.

### 3.3 Ошибки

Проверка до обращения к брокеру даёт `INVALID_INPUT` с понятным текстом:
- файл не найден или не читается (с путём);
- неверный пароль хранилища или ключа;
- ключ зашифрован, а пароль не задан: «ключ зашифрован — укажите пароль»;
- ключ не соответствует сертификату;
- сертификат истёк или ещё не действует (с датами);
- в JKS несколько ключей и не указан alias (со списком alias).

Ошибки рукопожатия TLS от librdkafka переводятся в понятные сообщения:
- брокер не принял клиентский сертификат;
- сертификат брокера не подписан указанным CA;
- имя хоста не совпадает с сертификатом.

Исходный текст остаётся в «Подробностях».

### 3.4 Интерфейс

В форме подключения (протоколы SSL и SASL_SSL):
- блок «Доверенный CA»: путь, формат, пароль;
- блок «Клиентский сертификат»: включатель, формат (автоопределение по расширению: `.pem`/`.crt`/`.key` → PEM, `.p12`/`.pfx` → PKCS#12, `.jks` → JKS), пути с кнопкой выбора файла (`tauri-plugin-dialog`), пароли, alias.

У каждого поля видимая подпись. Кнопка «Проверить подключение» уже есть и показывает ошибки из 3.3.

### 3.5 Тесты

- Скрипт `dev/certs/generate.sh` создаёт CA, серверный и клиентский сертификаты: клиентский в PEM (с паролем и без), PKCS#12 (с паролем и без) и JKS.
- `dev/docker-compose.yml` получает mTLS-листенер (`ssl.client.auth=required`).
- Unit-тесты: разбор и конвертация каждого формата, каждая ошибка из 3.3.
- Интеграционный тест `it_mtls`: подключение по каждому формату, отказ без клиентского сертификата.

## 4. Блок 2 — лицензии

### 4.1 Ключ

Формат: `base64url(payload) "." base64url(signature)`, подпись Ed25519.

```
payload (JSON) {
  v: 1,
  id: string,                         // уникальный id лицензии
  tier: "pro",
  kind: "personal" | "organization",
  licensee: string,                   // e-mail или название организации
  issued: "YYYY-MM-DD",
  expires: "YYYY-MM-DD" | null,
  seats: number | null                // условие договора, офлайн не проверяется
}
```

- Открытый ключ вшит в приложение. Проверка полностью офлайновая.
- Ключ с неизвестной версией `v`, неверной подписью или испорченным форматом даёт состояние «ключ недействителен» с причиной и тариф Free.

### 4.2 Источник и хранение

1. Ключ из корпоративной политики (`licenseKey`) — высший приоритет. В интерфейсе он только для чтения, с меткой «Управляется вашей организацией».
2. Личный ключ вводится на экране «Лицензия» и хранится в `license.json` в данных приложения (это не секрет). Есть кнопка «Удалить ключ».

### 4.3 Проверка и границы

- Команда `license_status` возвращает: тариф, источник (`policy` или `user`), владельца, срок, состояние (`valid`, `expiring` — меньше 14 дней, `expired`, `invalid` с причиной).
- `require_pro` в Rust вызывается в `start_consumer`, `commit_offsets`, `pause_partitions`, `resume_partitions` и в `save_connection`, если окружение меняется на `prod` или создаётся новый prod-профиль. Без лицензии возвращается новый код ошибки `PRO_REQUIRED`. Интерфейс только отображает состояние. Ограничение нельзя обойти, вызвав команду напрямую.
- Guard изменений (`read_only` и подтверждения prod) от лицензии **не зависит** (см. §2).
- `expiring`: баннер на экране «Лицензия» и ненавязчивое уведомление при запуске. `expired`: Pro-функции блокируются, данные не трогаются.
- Время берётся из системных часов. Защита от перевода часов назад не делается.

### 4.4 Утилита выдачи

`tools/issue-license` — отдельный бинарник в рабочем пространстве Cargo. В сборку приложения не входит.
- `issue-license keygen --out <dir>` создаёт пару ключей. Закрытый ключ хранится только у владельца и в репозиторий не попадает (`.gitignore`, проверка в CI).
- `issue-license issue --key <private> --kind organization --licensee "ACME" --expires 2027-03-31 [--seats 500]` печатает ключ.
- `issue-license verify <key>` печатает payload и результат проверки подписи.

## 5. Блок 3 — корпоративная политика

### 5.1 Источники

Политика читается один раз при запуске (модуль `src-tauri/src/policy/`):

| ОС | Источник |
|---|---|
| macOS | `/Library/Managed Preferences/<identifier>.plist` (пишет MDM) |
| Windows | `HKLM\Software\Policies\<Vendor>\<Product>` (GPO / Intune) |
| Linux | `/etc/<identifier>/policy.json` |

Пользовательских уровней (HKCU, `~/Library/Preferences`) нет: политику задаёт только администратор.

### 5.2 Ключи

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `updatesEnabled` | bool | `true` | `false`: никаких запросов к серверу обновлений |
| `updateUrl` | string | публичный `latest.json` | внутреннее зеркало с одобренными версиями |
| `licenseKey` | string | — | ключ организации (§4.2) |

- Неизвестные ключи пишутся в лог и игнорируются: старая версия не ломается от политики, рассчитанной на новую.
- **Повреждённая политика:** если источник существует, но не разбирается, то `updatesEnabled = false` (безопасно закрыто), остальные значения по умолчанию, а в «О программе» и «Обновления» видна ошибка политики. Если администратор задал политику, он хотел ограничений.
- Команда `policy_status`: признак «управляется организацией», действующие значения, ошибка разбора.

## 6. Блок 4 — релиз

### 6.1 Имя и идентификатор

Окончательное имя выбирается до первого публичного релиза. Кандидаты и ограничения:
- товарный знак Apache — форма «<Бренд> for Apache Kafka», без «of»;
- проверить занятость имени.

Имя, короткое имя, `identifier` (рабочий вариант `io.github.vvnovg.<brand>.kafka`), имя сервиса в хранилище секретов и вендор для реестра задаются **в одном месте**: `tauri.conf.json` и модуль `src-tauri/src/product.rs`. Остальной код берёт их оттуда.

**Миграция со старого идентификатора** `dev.kafkaexplorer.app`. При первом запуске, если новые данные пусты, а старые есть:
- копируются `connections.json`, `templates.json` и `history/`;
- секреты переносятся из сервиса `kafka-explorer` в новый.

Старое не удаляется, чтобы можно было откатиться. Результат пишется в лог. Миграция идемпотентна.

### 6.2 Сборка (GitHub Actions)

Workflow в приватном репозитории запускается по тегу `v*`:

| ОС | Раннер | Артефакты |
|---|---|---|
| macOS arm64 | `macos-14` | `.dmg`, `.pkg`, `.app.tar.gz` (для обновлений) |
| macOS x86_64 | `macos-13` | то же |
| Windows x64 | `windows-latest` | `.msi` (установка на машину, тихий режим `/qn`), архив для обновлений |
| Linux x64 | `ubuntu-22.04` | `.deb`, `.rpm`, `.AppImage` |

Итог: GitHub Release в **публичном репозитории релизов** (только установщики, `latest.json` и README) с описанием из `CHANGELOG.md`. CI проверяет, что версия в теге, `package.json`, `Cargo.toml` и `tauri.conf.json` совпадает.

**Главный риск — сборка librdkafka (rdkafka-sys) на Windows.** Первая задача плана проверяет сборку всех трёх ОС в CI, до остальной работы.

### 6.3 Подпись

- **Ключ updater** (Tauri, Ed25519) обязателен с первого релиза. Он хранится в секретах GitHub, а публичная часть — в `tauri.conf.json`. Без него сборка падает.
- **Apple** (Developer ID, нотаризация) и **Windows** (сертификат или Azure Trusted Signing) подключаются, если в CI заданы секреты. Без них установщики собираются неподписанными, а в журнале сборки появляется предупреждение.

### 6.4 Обновления

- `tauri-plugin-updater`. Проверка при запуске (без блокировки интерфейса) и пункт «Проверить обновления».
- Найдено обновление → описание версии и кнопка «Установить и перезапустить». Если идёт consumer-сессия или пакетная отправка, сначала предупреждение.
- Политика `updatesEnabled = false`: проверка не выполняется, вместо кнопки — «Обновления управляются вашей организацией». `updateUrl` подменяет адрес.
- Ошибка сети при проверке не мешает работе: в лог и тихая метка «не удалось проверить».

### 6.5 «О программе», логи, диагностика

- «О программе»: версия, сборка (commit), тариф и владелец лицензии, состояние политики, путь к логам.
- Логи: стандартная папка логов ОС, ротация 5 файлов по 5 МБ, уровень `info` (`debug` через `RUST_LOG`).
- **Пароли, ключи, содержимое сертификатов и лицензионный ключ в лог не попадают.** Тест проверяет лог после подключения с SASL и mTLS.
- «Собрать диагностику» сохраняет zip через системный диалог:
  - логи;
  - версия, ОС, архитектура;
  - профили подключений без секретов (пути к сертификатам остаются);
  - состояние политики;
  - состояние лицензии без самого ключа.
- Телеметрии и отчётов о сбоях нет. Наружу приложение ходит только к брокерам и, если включено, к серверу обновлений.

### 6.6 Документация

- `README.md` (публичного репозитория релизов): установка на каждой ОС, включая запуск неподписанной версии (Gatekeeper, SmartScreen), и где взять Pro-ключ на время беты.
- `docs/admin.md`:
  - раздача через Jamf/Intune/SCCM;
  - ключи политики с примерами `.mobileconfig`, `.reg` и `policy.json`;
  - сетевые адреса;
  - тихая установка;
  - расположение данных и логов.
- `docs/licensing.md` (для владельца): генерация ключей, выдача, хранение закрытого ключа.

### 6.7 Проверка релиза

- Автоматически в CI на каждой ОС: unit-тесты Rust и фронтенда, сборка. Интеграционные тесты с Kafka запускаются только на Linux (Docker).
- Вручную перед релизом, по чек-листу в `docs/release-checklist.md`, на трёх ОС: установка, запуск, подключение (PLAINTEXT и mTLS), обновление с предыдущей версии, работа с политикой `updatesEnabled = false`.

## 7. Вне M3

Локализация и тексты на английском (B), подсказки (C), руководство пользователя (D), оплата (F₂), отчёты о сбоях, телеметрия, Kerberos, OAuth, MSK IAM, Schema Registry. Отложенные Minor из M2b (`m2b-final-review.md`) не входят, кроме тех, что затронуты этим этапом.

Язык интерфейса M3 остаётся русским. Английский как язык Free появляется в подпроекте B, до первого **внешнего** публичного релиза. Бета M3 рассчитана на корпорацию, где работает автор.
