# Glafira for Apache Kafka — этап G2 «Проверка кластера и замечания»

**Дата:** 2026-10-19
**Зачем:** человек и LLM видят проблемы кластера одним списком. Glafira сама проверяет кластер детерминированными
правилами («находки»), а LLM через MCP объясняет их, связывает и оставляет свои «замечания» об объектах. Всё это
показывается в интерфейсе рядом с объектами. Кластер при этом не меняется: G2 ничего не пишет в Kafka.

**Этапы MCP-шлюза:** G1 — шлюз только для чтения (готов, `2026-10-18-glafira-mcp-gateway-g1-design.md`);
G2 — эта спека; G3 — предложения LLM, которые открываются заполненными формами; G4 — выборка сообщений с маскировкой,
сравнение кластеров, MCP prompts и resources.

## 1. Решения

| Вопрос | Решение |
|---|---|
| Тариф | Проверка кластера в интерфейсе и инструмент `health_check` — Free. Замечания LLM (`annotate`, `list_annotations`, `remove_annotation`) — Pro |
| Когда идёт проверка | Только по запросу: кнопка «Проверить кластер» или вызов `health_check`. Автоматических и периодических проверок нет |
| Строгость | Своя у каждого правила для каждого окружения подключения (`local`, `dev`, `test`, `stage`, `prod`). Порогов и настроек правил нет; человек может скрыть находку для конкретного объекта |
| Правила | Четыре группы: брокеры и партиции, надёжность топиков, конфиг брокеров, consumer groups (§4) |
| Срок замечаний LLM | Хранятся на диске по подключению до закрытия человеком или LLM, но не дольше 7 дней с создания |
| Показ | Вкладка «Замечания» у подключения, значки в дереве и списках топиков и групп, блок замечаний на экранах кластера, топика и группы |
| Где движок | Модуль приложения `src-tauri/src/health/`: сборщик снимка, чистые функции правил, хранилище. Отдельного крейта нет |
| MCP | Четыре новых инструмента в крейте `glafira-mcp` (всего 16); типы ответов — свои, типы приложения к LLM не попадают, как в G1 |
| Изменение кластера | Нет. Правила только читают, замечания пишутся в файл Glafira |
| Документация | Новая глава руководства `health-check`, правка главы `llm-mcp`, все строки — на 12 языках внутри G2 |

## 2. Архитектура

```
 Интерфейс ── «Проверить кластер» ─┐                ┌── health_check (Free)
                                    ▼                ▼
                     health::Checker (одна проверка на подключение, общий результат)
                        │ snapshot.rs ── kafka::* (только чтение) ──► Kafka
                        │ rules/*.rs  ── чистые функции над ClusterSnapshot
                        ▼
                     health::Store  ◄── annotate / list_annotations / remove_annotation (Pro)
                        │ health/<connectionId>.json
                        └── событие health://changed ──► панель, значки, блоки
```

- `src-tauri/src/health/mod.rs` — `Checker`: запуск проверки, ожидание уже идущей, дедлайн, событие.
- `health/snapshot.rs` — `ClusterSnapshot` и его сборка через существующие `kafka::cluster`, `kafka::topics`,
  `kafka::configs`, `kafka::group_ops`. Для конфигов топиков добавляется пакетный `kafka::configs::describe_configs_many`
  (до 100 ресурсов за запрос); сейчас есть только вызов на один ресурс.
- `health/rules/{brokers,topics,broker_configs,groups}.rs` — правила: `fn(&ClusterSnapshot, Environment) -> Vec<Finding>`.
  `health/rules/mod.rs` — реестр `RULES` и константа `RULE_IDS`.
- `health/store.rs` — последняя проверка, скрытые находки, замечания LLM; срок, лимиты, атомарная запись.
- `src-tauri/src/commands/health.rs` — команды интерфейса (§7).
- Крейт `glafira-mcp`: `Backend` получает метод `health(&self, op: HealthOp) -> BoxFuture<Result<HealthOutput, BackendError>>`
  и `fn pro_active(&self) -> bool`. `HealthOp` — `Check { … }`, `Annotate { … }`, `ListAnnotations { … }`,
  `RemoveAnnotation { … }`. Ни одна операция не меняет кластер: реализация в `src-tauri/src/mcp/backend.rs` вызывает только
  `health::Checker` (чтение) и `health::Store` (файл Glafira). Тест `tests/manifest.rs` по-прежнему запрещает крейту
  зависимость от `rdkafka` и приложения.

## 3. Снимок кластера и лимиты

`ClusterSnapshot` собирается по шагам; каждый шаг укладывается в общий дедлайн:
1. Метаданные (один запрос): `clusterId`, контроллер, брокеры, все топики с партициями (`leader`, `replicas`, `isr`).
   Правила партиций и RF работают по всем топикам без ограничения.
2. Конфиги всех брокеров (`DescribeConfigs` по брокеру).
3. Конфиги топиков пакетами по 100, не больше 2000 топиков: сначала внутренние, затем по имени. У каждого значения —
   источник (`source`), чтобы находка показала, задано ли значение у топика или унаследовано.
4. Список групп; описание и лаг — не больше 500 групп по `groupId` (пакетами по 50).

Лимиты:
- одна проверка на подключение одновременно; второй вызов (интерфейс, другая сессия MCP) ждёт идущую и получает тот же
  результат;
- не больше 4 одновременных запросов к Kafka внутри проверки;
- общий дедлайн 45 с (ниже 60 с — таймаута клиентов на TypeScript SDK). По истечении правила считаются по тому, что
  собрано, проверка помечается `incomplete`, непроверенные части перечисляет находка `check.partial`;
- объект, данные которого не прочитаны (ошибка `DescribeConfigs` у топика, ошибка описания группы), считается
  непроверенным: правила по нему не срабатывают, находка `check.partial` называет число и причину. Ложных находок по
  непрочитанным данным нет;
- чувствительные значения (`isSensitive`, маска по имени из G1 `rules::mask`) в снимок не попадают.

## 4. Каталог правил

Обозначения: **К** — `critical`, **П** — `warning`, **И** — `info`, «—» — правило в этом окружении не срабатывает.
Столбец «прочие» — `test`, `dev`, `local`. Объект находки (`target`) — `cluster`, `broker`, `topic` или `group`;
находки по партициям собираются в одну находку на топик.

| `ruleId` | Объект | Условие | prod | stage | прочие |
|---|---|---|---|---|---|
| `cluster.noController` | cluster | контроллер неизвестен | К | К | К |
| `partition.offline` | topic | есть партиции без лидера; в параметрах — номера (до 20) | К | К | К |
| `partition.underReplicated` | topic | есть партиции с ISR меньше реплик; номера (до 20) | К | П | И |
| `cluster.singleBroker` | cluster | ровно один брокер | К | П | — |
| `broker.leaderSkew` | broker | среднее лидеров на брокер ≥ 10 и у брокера лидеров больше или меньше среднего более чем на 20 % | П | П | — |
| `partition.notPreferredLeader` | cluster | есть партиции, где лидер — не первая реплика; одна находка с числом и примерами (до 10) | И | И | — |
| `topic.replicationFactorOne` | topic | RF = 1 (включая внутренние топики) | К | П | — |
| `topic.minIsrUnreachable` | topic | `min.insync.replicas` > RF — запись с `acks=all` невозможна | К | К | П |
| `topic.minIsrEqualsRf` | topic | `min.insync.replicas` = RF > 1 — падение одной реплики останавливает запись с `acks=all` | П | П | — |
| `topic.minIsrOne` | topic | `min.insync.replicas` = 1 при RF ≥ 3 | П | И | — |
| `topic.uncleanElection` | topic | `unclean.leader.election.enable` = `true` | П | И | — |
| `broker.autoCreateTopics` | cluster | `auto.create.topics.enable` = `true` | П | И | — |
| `broker.defaultReplicationFactorOne` | cluster | `default.replication.factor` = 1 при ≥ 3 брокерах | П | И | — |
| `broker.defaultMinIsrOne` | cluster | `min.insync.replicas` = 1 у брокера при ≥ 3 брокерах | П | И | — |
| `broker.configDrift` | cluster | значение важного ключа различается между брокерами; одна находка на ключ со значениями по брокерам | П | П | И |
| `group.abandoned` | group | состояние `Empty`, суммарный лаг > 0 | П | П | И |
| `group.rebalancing` | group | состояние `PreparingRebalance` или `CompletingRebalance`; подсказка про `observe_consumer_group` | И | И | И |
| `group.idleMembers` | group | классическая группа в `Stable`, у части участников нет партиций | И | И | И |
| `group.lagGrowing` | group | прошлая проверка была от 1 мин до 24 ч назад и `lagNow − lagPrev ≥ max(1000, lagPrev × 0,5)` | П | П | И |
| `check.partial` | cluster | проверка обрезана лимитом, дедлайном или ошибками чтения | И | И | И |

Уточнения:
- значения `broker.*` (кроме `configDrift`) берутся у брокера-контроллера, а если он неизвестен — у брокера с меньшим id;
- важные ключи `broker.configDrift`: `default.replication.factor`, `min.insync.replicas`, `auto.create.topics.enable`,
  `unclean.leader.election.enable`, `num.partitions`, `log.retention.ms`, `log.retention.hours`, `message.max.bytes`;
  сравниваются брокеры, чьи конфиги прочитаны;
- для `topic.minIsr*` и `topic.uncleanElection` в параметрах — значение и его источник (у топика или унаследовано);
- для групп протокола `consumer` (KIP-848) librdkafka 2.12 показывает переходные состояния как `Unknown`, поэтому
  `group.rebalancing` для них может не сработать — это отмечено в тексте правила для LLM;
- `group.lagGrowing` берёт `lagPrev` из прошлой проверки этого подключения (§5).

Находка правила: `{ key, ruleId, severity, target { kind, name? }, params }`. `key` — `ruleId` + объект; по нему работают
скрытие и значки. Тексты в интерфейсе строятся из ключей `health.rules.<ruleId>.title`, `.details`, `.fix` с параметрами
(12 языков); LLM получает английские `title` и `details` из Rust (`health/texts.rs`). Тест Rust проверяет, что для каждого
`RULE_IDS` в `src/locales/en.json` есть все три ключа.

## 5. Находки, замечания и хранение

Файл `health/<connectionId>.json` в каталоге данных, права 0600, атомарная запись (временный файл + переименование),
`schemaVersion: 1`. Удаляется вместе с подключением; в экспорт и импорт подключений не входит. Повреждённый файл
переименовывается в `<connectionId>.json.bad`, работа продолжается с пустым состоянием, в лог — предупреждение.

```
{ schemaVersion, lastCheck?, ignored [{ key, atMs }], annotations [...] }
```

**Последняя проверка** (`lastCheck`): `runId`, `startedAtMs`, `durationMs`, `trigger` (`ui` или `mcp` с именем клиента),
`environment`, `incomplete`, `scope { brokers, topicsChecked, topicsTotal, groupsChecked, groupsTotal }`, `findings [...]`,
`groupLag { groupId: totalLag }` (для `group.lagGrowing`). Новая проверка заменяет прошлую целиком.

**Скрытые находки** (`ignored`): ключи находок, которые человек скрыл кнопкой «Скрыть для этого объекта». Скрытые не
показываются и не считаются в значках; переключатель «Показать скрытые (N)» показывает их с кнопкой «Вернуть».
В `health_check` они приходят с `ignored: true`. Скрытие бессрочное, до «Вернуть».

**Замечание LLM** (`annotation`):
`{ id, target { kind, name? }, severity, title, body, relatedRuleId?, client, sessionId?, createdAtMs, updatedAtMs,
status, closedAtMs?, closedBy? }`:
- `title` — до 120 символов, `body` — до 2000; длиннее — обрезается с «…»; управляющие символы, кроме перевода строки,
  удаляются; разметка не интерпретируется;
- `client` — имя клиента, которое человек видел в диалоге подтверждения G1; у безымянного клиента — `null` и `sessionId`;
- `status` — `open`, `resolved` («Решено»), `dismissed` («Не актуально»); `closedBy` — `user`;
- повторный `annotate` того же клиента с тем же объектом и заголовком (без учёта регистра и пробелов по краям) среди
  открытых обновляет `severity`, `body`, `relatedRuleId`, `updatedAtMs` и отвечает `created: false`;
- не больше 200 открытых замечаний на подключение, дальше — `limit_reached`;
- любое замечание удаляется через 7 дней после `createdAtMs` (при чтении и записи файла);
- человек: «Решено», «Не актуально», «Удалить», «Удалить все замечания LLM» у подключения;
- LLM: `remove_annotation` удаляет только свои — того же `client`, а безымянный — только в той же сессии.

**Pro и доступ.** Создание замечаний требует Pro в момент вызова (`license.require_pro()`). Если лицензия закончилась,
оставленные замечания видны и закрываются как обычно, новые не создаются. Все инструменты G2 требуют подтверждённого
клиента и `llmAccess ≠ off` у подключения, как в G1. При выключенном `llmAccess` замечания остаются, но LLM их не видит
и не добавляет.

## 6. MCP-инструменты

| Инструмент | Тариф | Параметры | Ответ |
|---|---|---|---|
| `health_check` | Free | `connectionId`, `maxAgeSeconds = 300` (0–3600), `runId?`, `ruleIds?`, `minSeverity = info`, `includeIgnored = true`, `offset = 0`, `limit = 100` (≤ 200) | `runId`, `startedAtMs`, `durationMs`, `trigger`, `environment`, `incomplete`, `scope`, `summary [{ ruleId, severity, count }]`, `findings { total, items [{ key, ruleId, severity, target, title, details, params, ignored }], nextOffset? }` |
| `annotate` | Pro | `connectionId`, `target { kind, name? }`, `severity` (`info`/`warning`/`critical`), `title`, `body`, `relatedRuleId?` | `{ annotationId, created }` |
| `list_annotations` | Pro | `connectionId`, `status = open` (`open`/`closed`/`all`) | `{ items [{ id, target, severity, title, body, client, status, createdAtMs, updatedAtMs, closedBy? }] }` |
| `remove_annotation` | Pro | `connectionId`, `annotationId` | `{ removed: true }` |

- `health_check`: если последней проверке меньше `maxAgeSeconds`, новая не запускается; с `runId` возвращает страницы этой
  проверки (`not_found`, если она уже заменена); `summary` — по всем находкам проверки, `findings` — с учётом фильтров;
  предел ответа 100 KB с усечением, как в G1. Для лимитов G1 вызов — одна операция, занимает один слот параллельности
  сессии; внутренние запросы проверки — под лимитом §3.
- `annotate`: объект сверяется с кластером — топик и брокер по метаданным, группа по списку групп, `cluster` без имени;
  нет объекта — `not_found`; `relatedRuleId` должен быть из `RULE_IDS`, иначе `invalid_argument`.
- Подсказки инструментов: у `annotate` и `remove_annotation` — `readOnlyHint: false`, `destructiveHint: false`,
  `idempotentHint: true`, `openWorldHint: false`; остальные, как в G1, `readOnlyHint: true`.
- В Free инструменты замечаний остаются в списке; вызов отвечает `pro_required` с текстом
  `Annotations require Glafira Pro; report findings in the chat instead`. Список инструментов при смене лицензии не
  перечитывается.
- `instructions` сервера дополняются: (1) начинать ревью с `health_check`, факты брать из него, а модель объясняет их,
  расставляет приоритеты и связывает; (2) замечания пишутся в Glafira и видны человеку рядом с объектами, кластер не
  меняется; (3) не дублировать находки правил замечаниями — дополнять их выводами со ссылкой `relatedRuleId`;
  (4) находки с `ignored: true` человек решил не трогать.
- Новые коды ошибок: `pro_required`, `limit_reached`, `check_in_progress_timeout` (не дождались чужой проверки за 45 с).
- Журнал (`mcp-audit.jsonl`): `health_check` — с `runId`, числом находок и признаком «повторно использована»;
  `annotate` и `remove_annotation` — с `annotationId`, объектом и строгостью. Тексты замечаний в журнал не пишутся.
- Тест-«сторожок» сверяет точный список из 16 инструментов.

## 7. Интерфейс

- **Обзор кластера:** кнопка «Проверить кластер»; строка «Последняя проверка: 5 мин назад · claude-ai · К 2 · П 5 · И 3»
  со ссылкой «Все замечания»; пометка «проверено частично», если `incomplete`; блок «Замечания» с находками уровня
  `cluster` и `broker`.
- **Вкладка «Замечания»** (`{ kind: "findings", connectionId }`) открывается из ссылки, значка в дереве и контекстного
  меню подключения:
  - панель инструментов: «Проверить кластер», время, автор и объём последней проверки;
  - фильтры: строгость, источник («Правила» / «LLM»), вид объекта, поиск по имени; «Показать скрытые (N)»;
  - находки правил сгруппированы по `ruleId` (группа сворачивается: «RF = 1 — 300 топиков»); у находки — иконка и цвет
    строгости, объект-ссылка (топик и группа открывают свои вкладки, брокер и кластер — обзор кластера), пояснение,
    «что делать», «Скрыть для этого объекта»;
  - замечания LLM — отдельный раздел с подписью «Замечание LLM · claude-ai», текст как есть (переводы строк сохраняются,
    ссылки не кликабельны), действия «Решено», «Не актуально», «Удалить»; свёрнутый раздел «Закрытые»; кнопка «Удалить
    все замечания LLM»; в Free вместо раздела — `ProLock`.
- **Значки:** в дереве подключений — число открытых и не скрытых находок и замечаний уровня К и П, цвет — по высшей
  строгости; в списках топиков и групп — колонка с иконкой высшей строгости и числом, во всплывающей подсказке — заголовки.
- **Экраны топика и группы:** блок «Замечания» сверху с находками и замечаниями этого объекта и теми же действиями.
- **Обновление:** событие Tauri `health://changed { connectionId }` после проверки и любого изменения замечаний;
  панель, значки и блоки перечитывают данные. Замечание LLM появляется без перезагрузки.
- **Команды:** `run_health_check(connectionId)`, `get_health(connectionId)` (последняя проверка, скрытые, замечания с
  учётом срока), `set_finding_ignored(connectionId, key, ignored)`, `close_annotation(connectionId, id, status)`,
  `delete_annotation(connectionId, id)`, `delete_llm_annotations(connectionId)`.
- **Справка:** F1 на вкладке «Замечания» — глава `health-check`; подсказки «?» у «Проверить кластер» и «Показать скрытые».

## 9. Ошибки

- Проверка не запустилась (нет связи, ошибка метаданных): баннер ошибки с «Повторить», прошлая проверка остаётся.
- Частичные ошибки чтения — §3: объект непроверен, `check.partial`.
- Ошибка записи файла: команда или инструмент возвращает ошибку `internal` с общим текстом для LLM (путь к файлу не
  раскрывается, как в G1), в интерфейсе — баннер.
- Повреждённый файл — §5.

## 10. Тесты

- **Правила** (`cargo test --lib`): табличные тесты на снимках-фикстурах; каждое правило — во всех пяти окружениях;
  матрица строгости сверяется с таблицей §4; граничные значения (ровно 20 %, среднее 9 и 10, `lagPrev` 0 и 2000, прошлая
  проверка 59 с и 24 ч + 1 с); непрочитанные объекты не дают находок.
- **Хранилище:** срок 7 дней, обновление вместо дубля, лимит 200, скрытие и возврат, снятие только своих, безымянный
  клиент и сессия, атомарная запись, повреждённый файл, удаление вместе с подключением.
- **Сборщик и `Checker`:** фейковый источник — лимиты 2000 и 500, пакеты, дедлайн 45 с, ожидание идущей проверки,
  частичные ошибки, отсутствие чувствительных значений.
- **Крейт MCP** (`tests/server.rs`, фейковый `Backend`): `pro_required`, `not_found`, `limit_reached`, `invalid_argument`,
  страницы по `runId`, `maxAgeSeconds`, фильтры, предел 100 KB, `check_in_progress_timeout`, «сторожок» 16 инструментов,
  подсказки `readOnlyHint`.
- **Интеграция** `src-tauri/tests/it_health.rs` (dev-стенд): топик RF = 1, топик с `min.insync.replicas=2` при RF = 1,
  пустая группа с лагом; проверка с окружением `prod` даёт `topic.replicationFactorOne`, `topic.minIsrUnreachable`,
  `group.abandoned`, `cluster.singleBroker`.
- **Фронтенд:** вкладка, фильтры, группировка, скрытие и возврат, действия с замечаниями, значки в дереве и списках, блоки
  на экранах, `ProLock` в Free, обновление по событию, F1.
- **Скрипты:** `pnpm i18n:check` с новой главой; тест Rust на ключи `health.rules.*` в `en.json`.
- **Смоук** `docs/smoke/g2.md`.

## 11. Риски

| Риск | Мера |
|---|---|
| Шум на больших кластерах | Группировка по правилу, строгость по окружению, скрытие для объекта |
| Спам замечаний от LLM | Лимит 200, обновление вместо дубля, «Удалить все замечания LLM», срок 7 дней |
| Ложные срабатывания правил | Скрытие для объекта; LLM видит `ignored: true` |
| Нагрузка от конфигов 2000 топиков и лага 500 групп | Только по запросу, `maxAgeSeconds`, 4 запроса одновременно, дедлайн 45 с |
| Prompt injection через имена объектов в находках | `instructions` G1 о недоверенных данных; текст LLM в интерфейсе — обычный текст с подписью клиента |
| Расхождение английских текстов Rust и `en.json` | Тест на наличие ключей; тексты для LLM — короткие, интерфейс берёт свои из словарей |
