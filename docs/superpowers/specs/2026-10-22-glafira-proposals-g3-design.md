# Glafira for Apache Kafka — этап G3 «Предложения LLM в формах»

**Дата:** 2026-10-22
**Зачем:** после проверки кластера LLM-ассистент не только объясняет находки, но и предлагает исправление:
изменить конфиги топика, создать топик, добавить партиции, сбросить оффсеты группы. Предложение появляется в Glafira
рядом с замечаниями; человек открывает его уже заполненной формой приложения, правит, что хочет, и подтверждает как
обычно. Ни одна запись в Kafka не идёт мимо явного подтверждения в интерфейсе: инструмент MCP пишет только файл Glafira.

**Этапы MCP-шлюза:** G1 — шлюз только для чтения (готов, `2026-10-18-glafira-mcp-gateway-g1-design.md`);
G2 — проверка кластера и замечания (готов, вошёл в 0.3.0, `2026-10-19-glafira-health-annotations-g2-design.md`);
G3 — эта спека; G4 — выборка сообщений с маскировкой, сравнение кластеров, MCP prompts и resources.

**Изменение контекста:** с 0.3.0 все функции бесплатны. Деление Free/Pro из спек G1 и G2 не действует,
в этой спеке тарифа нет.

## 1. Решения

| Вопрос | Решение |
|---|---|
| Что предлагает LLM | Четыре вида изменений: конфиги топика, создание топика, добавление партиций, сброс оффсетов группы. Удаление и очистка топика, удаление группы, отправка сообщений — нет: разрушительные действия и данные остаются только за человеком |
| Кто меняет кластер | Только человек через существующие формы и их стражи (read-only, ввод имени для prod). Инструмент MCP записывает предложение в файл Glafira и ничего больше |
| Где показывается | Раздел «Предложения LLM» на вкладке «Замечания», блок «Замечания» на экранах топика и группы, значки в дереве и списках — как у замечаний |
| Как замыкается цикл | Кнопка «Открыть в форме» открывает форму с заполненными полями; статус «применено» ставит Rust в команде изменения после успеха операции, фронтенд поставить его не может |
| Доступ | `llmAccess = metadata` достаточно, нового уровня нет: предложение кластер не меняет. Для read-only подключения предложение создаётся, но кнопка формы неактивна, а модель получает `readOnly: true` |
| Строгость | У предложения есть `severity`, как у замечания: работают существующие значки, фильтры и цвета |
| Хранение | В `health/<connectionId>.json` рядом с замечаниями: срок 7 дней с создания, не больше 50 открытых на подключение, повтор того же автора по тому же объекту обновляет предложение |
| MCP | Три новых инструмента (`propose_change`, `list_proposals`, `withdraw_proposal`), всего 19; типы ответов — свои, типы приложения к LLM не попадают |
| Хвосты G2 | Остатки финальной волны G2 по вкладке «Замечания» и правилу `cluster.noController` — первая задача плана (§9) |
| Документация | Раздел в главе `health-check`, правка главы `llm-mcp`, README, все строки — на 12 языках внутри G3 |

## 2. Архитектура

```
 LLM ── propose_change / list_proposals / withdraw_proposal ──► crates/glafira-mcp (ProposalOp)
                                                                     │ Backend::proposals
                                                                     ▼
            src-tauri/src/mcp/backend.rs: факты из кластера (только чтение) → health::proposals::validate
                                                                     │
                                                                     ▼
            health::Store  ── proposals в health/<id>.json ──► событие health://changed
                 ▲                                                   │
                 │ mark_applied(proposalId)                          ▼
   commands::{topic_ops, groups} ◄── форма с proposalId ◄── вкладка «Замечания» / блок объекта: «Открыть в форме»
                 │
                 ▼ (только после подтверждения человека, с теми же стражами)
               Kafka
```

- `src-tauri/src/health/proposals.rs` (новый) — типы `Change` и `Proposal`, статусы, чистая проверка
  `validate(&Change, &Facts) -> Result<(), ProposalError>` и сравнение `applied_as_proposed(&Change, &Applied) -> bool`.
  `Facts` — только то, что нужно для проверки: топики с числом партиций и признаком `internal`, число брокеров,
  имена ключей конфигов топика, список групп. Модуль не ходит в Kafka.
- `health/store.rs` — поле `proposals` в `HealthFile`; методы `propose`, `set_proposal_status`, `mark_applied`,
  `withdraw_proposal`, `delete_proposal`, `delete_all_proposals`; срок и лимит; удаление вместе с подключением.
- `src-tauri/src/mcp/backend.rs` — реализация `Backend::proposals`: собирает `Facts` существующими функциями чтения
  (`kafka::cluster::cluster_metadata`, `kafka::configs::describe_topic_configs`, список групп), вызывает `validate`,
  пишет в `Store` через `HealthService::write` с поколением (как `annotate`).
- `src-tauri/src/commands/health.rs` — команды интерфейса (§6); `commands/topic_ops.rs` и `commands/groups.rs` —
  необязательный `proposal_id` у четырёх изменяющих команд и отметка «применено» (§6).
- Крейт `glafira-mcp`: модуль `proposals.rs` (`ProposalOp`, `ProposalOutput`, `ChangeSpec` со схемой для LLM,
  `ProposalView`), `server/proposal_tools.rs` — три инструмента; трейт `Backend` получает метод
  `proposals(&self, op: ProposalOp) -> BoxFuture<Result<ProposalOutput, BackendError>>`. Тест `tests/manifest.rs`
  по-прежнему запрещает крейту зависимость от `rdkafka` и приложения: в крейте нет ни одной операции записи в Kafka.
- Фронтенд: `components/health/ProposalItem.tsx` (карточка), `components/health/proposals.ts` (текст изменения,
  фильтры), раздел в `FindingsPanel.tsx`, предложения в `HealthBlock.tsx` и `findings.ts` (значки), поле `proposal`
  в `TabSpec` (`state/workspace.ts`), заполнение четырёх форм (§8).

## 3. Предложение: модель и хранение

```
Proposal {
  id, severity (info | warning | critical),
  title ≤ 120, rationale ≤ 2000,            // санитизация как у замечаний: управляющие символы, кроме перевода строки, удаляются
  target { kind: topic | group, name },     // выводится из change; для createTopic — имя будущего топика
  change,                                   // см. ниже
  relatedRuleId?, relatedFindingKey?,
  client, sessionId?,                       // автор: как у замечаний (имя клиента из диалога подтверждения или сессия безымянного)
  createdAtMs, updatedAtMs,
  status: open | applied | rejected | withdrawn, closedAtMs?,
  appliedAsProposed?: bool,                 // только у applied: применено без правок (true) или с правками (false)
  rejectReason?: ≤ 300                      // только у rejected: необязательный комментарий человека
}
```

**Виды изменения** (`change`, JSON с полем `kind`; одна и та же форма у LLM, в файле и во фронтенде):

| `kind` | Поля | Ограничения |
|---|---|---|
| `alterTopicConfigs` | `topic`, `changes [{ name, value }]` | 1–50 записей, имена без повторов; `value` — строка (установить) или `null` (вернуть значение по умолчанию); строка непустая, ≤ 1024 символов |
| `createTopic` | `name`, `partitions`, `replicationFactor?` (по умолчанию `-1` — значение брокера), `configs? { name: value }` | `partitions ≥ 1`; `replicationFactor ≥ 1` или `-1`; до 50 конфигов, значения ≤ 1024 символов |
| `addPartitions` | `topic`, `newTotal` | `newTotal` больше текущего числа партиций |
| `resetOffsets` | `groupId`, `strategy`, `scope` | те же типы, что у формы сброса: `strategy { type: earliest \| latest \| timestamp \| offset \| shift, timestampMs?, offset?, delta? }`, `scope { type: all \| topics \| partitions, topics?, partitions? [{ topic, partition }] }`; `offset ≥ 0`, `delta ≠ 0`, `timestampMs ≥ 0`; списки до 100 элементов |

**Жизненный цикл:**
- `open → applied` — только Rust в команде изменения после успеха (§6);
- `open → rejected` — человек («Отклонить», причина необязательна); `rejected → open` — человек («Открыть снова»);
- `open → withdrawn` — LLM (`withdraw_proposal`), только своё;
- `applied` и `withdrawn` — конечные; «Удалить» доступно человеку для любого статуса;
- любое предложение удаляется через 7 дней после `createdAtMs` при чтении и записи файла, как замечания.

**Повтор и лимит:** `propose_change` того же автора с тем же `kind` и тем же объектом (`target`) среди открытых
обновляет `severity`, `title`, `rationale`, `change`, `relatedRuleId`, `relatedFindingKey`, `updatedAtMs` и отвечает
`created: false`. Открытых предложений на подключение — не больше 50, дальше `limit_reached`. Повреждённый файл,
права и атомарная запись — как в G2 §5.

## 4. Инструменты MCP

| Инструмент | Параметры | Ответ |
|---|---|---|
| `propose_change` | `connectionId`, `severity`, `title`, `rationale`, `change`, `relatedRuleId?`, `relatedFindingKey?` | `{ proposalId, created, readOnly }` |
| `list_proposals` | `connectionId`, `status = open` (`open` / `closed` / `all`) | `{ items [{ id, severity, title, rationale, target, change, relatedRuleId?, relatedFindingKey?, client, status, createdAtMs, updatedAtMs, closedAtMs?, appliedAsProposed?, rejectReason? }], truncated, hint? }` |
| `withdraw_proposal` | `connectionId`, `proposalId` | `{ withdrawn: true }` |

- `propose_change`: `relatedRuleId` — из `rule_ids()`, иначе `invalid_argument`; `relatedFindingKey` — любая строка
  до 200 символов (ключ находки из `health_check`), не проверяется по проверке; `readOnly` — у подключения снят флажок
  изменений: применить сможет только человек, сначала сняв read-only. Проверка `change` против кластера — §5.
- `list_proposals`: сортировка по `updatedAtMs`, новые первыми; предел 100 КБ с усечением как у `list_annotations`
  (остаются самые свежие, `hint` — сузить по `status`).
- `withdraw_proposal`: чужое — `not_allowed`; нет такого — `not_found`; уже не открытое — `invalid_argument` с текущим
  статусом в тексте («proposal is already applied»). Безымянный клиент отзывает только из той же сессии (как
  `remove_annotation`).
- Подсказки: у `propose_change` и `withdraw_proposal` — `readOnlyHint: false`, `destructiveHint: false`,
  `idempotentHint: true`, `openWorldHint: false`; у `list_proposals` — `readOnlyHint: true`.
- Все три требуют подтверждённого клиента и `llmAccess ≠ off`, как инструменты G1 и G2; для лимитов G1 вызов —
  одна операция (чтение фактов для проверки — внутри этого слота).
- Журнал (`mcp-audit.jsonl`): у `propose_change` — `connectionId`, `kind`, `target`, `severity`, `relatedRuleId`;
  заголовок, обоснование и значения изменения не пишутся; у `withdraw_proposal` — `proposalId`.
- Описания инструментов по-английски, как в G1: предлагать после `health_check`, одна проблема — одно предложение,
  в `rationale` — объяснение для человека, кластер не меняется, пока человек не подтвердит в Glafira.
- `instructions` сервера дополняются: (1) изменения можно предлагать через `propose_change`; человек видит
  предложение рядом с объектом и применяет его сам заполненной формой — модель не ждёт результата в том же вызове;
  (2) решение человека смотреть в `list_proposals` (`applied`, `rejected` с причиной, `appliedAsProposed`);
  (3) при `readOnly: true` попросить человека снять флажок, а не искать обход; (4) удаление, очистка и отправка
  сообщений через Glafira не предлагаются — только описываются словами; (5) напоминание о недоверенных данных из G1
  остаётся. Первый абзац про «read-only gateway» уточняется: шлюз не меняет кластер, предложения применяет человек.
- Тест-«сторожок» сверяет точный список из 19 инструментов.

## 5. Проверка предложения при создании

Проверка идёт против живого кластера, как `annotate` сверяет объект, и даёт `invalid_argument` с понятным текстом.
Нарушение правила ниже — ошибка; значения конфигов Kafka проверяет сама при применении, её ошибку человек увидит
в форме.

- Общее: топик с `internal: true` в метаданных (например, `__consumer_offsets`) менять нельзя —
  «internal topics cannot be changed through Glafira»; имена обрезаются по краям и хранятся так, как их проверили.
- `alterTopicConfigs`: топик существует; каждое имя есть среди ключей `DescribeConfigs` этого топика (в ответе
  брокер перечисляет все известные ключи); имена не повторяются; у строки-значения — непустое содержимое.
  Совпадение с текущим значением ошибкой не считается: редактор покажет «изменений нет».
- `createTopic`: имя проходит `kafka::admin::validate_new_topic` (те же правила, что у формы); топика с таким именем
  нет («topic already exists»); `replicationFactor` не больше числа брокеров или `-1`.
- `addPartitions`: топик существует; `newTotal` больше текущего числа партиций («topic has N partitions; newTotal
  must be greater»).
- `resetOffsets`: группа есть в списке групп (`not_found`, если нет); стратегия и область проходят
  `kafka::groups::validate_reset_request`; топики области есть в метаданных, у партиций — индекс меньше числа партиций
  топика. Пустой группа быть не обязана: форма сама не даст применить сброс, пока группа не пуста.

Факты собираются одним проходом: метаданные кластера (топики, партиции, брокеры), конфиги топика только для
`alterTopicConfigs`, список групп только для `resetOffsets`. Ошибка чтения из Kafka уходит к LLM её кодом (`TIMEOUT`,
`AUTH_FAILED`, …), как в G1; текст про сертификаты для файловых ошибок не используется (§11).

## 6. Команды интерфейса и замыкание цикла

- `get_health(connectionId)` — `HealthView` получает `proposals` (все статусы, с учётом срока).
- `set_proposal_status(connectionId, proposalId, status: rejected | open, reason?)` — `rejected` с необязательной
  причиной (≤ 300 символов, санитизация как у текстов замечаний), `open` — «Открыть снова» для отклонённого;
  попытка открыть снова применённое или отозванное — ошибка `errors.health.proposalClosed`.
- `delete_proposal(connectionId, proposalId)`, `delete_all_proposals(connectionId)`.
- Все команды возвращают свежее состояние и шлют `health://changed`, пишут через `HealthService::write` с поколением
  (удалённое в промежутке подключение файла не получит), как команды G2.

**Отметка «применено».** Команды `alter_topic_configs`, `create_topic`, `add_partitions`, `reset_offsets` получают
необязательный параметр `proposal_id`; `reset_offsets` дополнительно — `request: Option<ResetRequest>` (стратегия
и область, которые показал предпросмотр) для сравнения с предложением. После успеха операции в Kafka команда:
1. находит открытое предложение с этим id того же `kind` и объекта; если его нет или оно закрыто — операция всё равно
   считается успешной, отметка пропускается, в лог приложения — предупреждение;
2. сравнивает применённое с предложенным: `alterTopicConfigs` — множество пар `(name, value | null)` без учёта порядка;
   `createTopic` — имя, партиции, фактор репликации и конфиги; `addPartitions` — `newTotal`; `resetOffsets` —
   `request` со стратегией и областью (без `request` — считается «с правками»);
3. записывает `status = applied`, `closedAtMs`, `appliedAsProposed`, шлёт `health://changed`.
Для `reset_offsets` отметка ставится, только если ни одна партиция не вернула ошибку; иначе предложение остаётся
открытым. Ошибка записи файла после успешной операции не отменяет её: команда возвращает результат операции, а ошибку
файла пишет в лог.

## 7. Интерфейс

**Вкладка «Замечания»:**
- новый раздел «Предложения LLM» между находками правил и замечаниями; фильтр «Источник» → «LLM» показывает
  предложения вместе с замечаниями, «Правила» скрывает оба; строгость, вид объекта и поиск по имени действуют на
  предложения так же, как на замечания;
- открытые — списком; закрытые (применённые, отклонённые, отозванные) — в свёрнутом «Закрытые (N)» раздела;
  пустое состояние «Предложений нет.»; кнопка «Удалить все предложения LLM» с подтверждением на странице (как у
  замечаний).

**Карточка предложения** (`ProposalItem`, стиль карточки замечания): значок строгости, заголовок, ссылка на объект
(у `createTopic` имя без ссылки — топика ещё нет), обоснование как есть (переводы строк сохранены, ссылки не
кликабельны), затем описание изменения на языке интерфейса, строится из `change`:
- `alterTopicConfigs`: «Конфиги топика:» и список `имя → значение` или `имя → по умолчанию`;
- `createTopic`: «Новый топик: N партиций, фактор репликации R (или «по умолчанию брокера»), конфиги `k=v`, …»;
- `addPartitions`: «Партиций: → N»;
- `resetOffsets`: «Оффсеты группы: <стратегия>, <область>» (стратегии и области — словами из формы сброса,
  время — в локальном формате).
Подпись «Предложение LLM · claude-code», при `relatedRuleId` — короткое имя правила; у закрытых — статус:
«Применено <когда>», «Применено с правками <когда>», «Отклонено» и причина, если есть, «Отозвано».
Действия: у открытого — «Открыть в форме» и «Отклонить» (разворачивает поле причины и кнопку подтверждения);
у отклонённого — «Открыть снова»; у любого — «Удалить». Для read-only подключения «Открыть в форме» неактивна с
подсказкой «Подключение только для чтения»; у `createTopic`, когда топик уже есть, кнопка активна — ошибку покажет
форма.

**Блоки «Замечания» на экранах топика и группы** показывают открытые предложения объекта теми же карточками без
ссылки на объект; у топика — предложения `alterTopicConfigs` и `addPartitions`, у группы — `resetOffsets`.
Предложения `createTopic` живут только на вкладке «Замечания».

**Значки** в дереве подключений и в списках топиков и групп считают открытые предложения вместе с замечаниями
(строгость К и П), в подсказке — их заголовки наравне с остальными.

**Обновление:** `health://changed` после каждой команды §6 и после отметки «применено» — карточки, значки и блоки
перечитывают данные; статус меняется без перезагрузки.

**Справка:** F1 на вкладке «Замечания» — глава `health-check` (раздел `proposals`); подсказка «?» у заголовка раздела
«Предложения LLM».

## 8. Открытие форм с заполнением

«Открыть в форме» открывает вкладку объекта с полем `proposal: { proposal, nonce }` в `TabSpec` (по образцу
`resetPrefill` и `ProducerPrefill`: `nonce` даёт повторному открытию заменить заполнение в уже открытой вкладке):

| `kind` | Вкладка | Что открывается |
|---|---|---|
| `alterTopicConfigs` | `topic` | подвкладка «Конфигурация», редактор включён; `ConfigEditor` получает начальные правки (`value` → установить, `null` → вернуть значение по умолчанию) и `proposalId`; обзор «было → станет» перед применением — как сейчас |
| `addPartitions` | `topic` | диалог добавления партиций открыт с `newTotal` в поле и `proposalId` |
| `createTopic` | `topics` | `CreateTopicForm` открыта: имя, партиции, фактор репликации; конфиги — в поле дополнительных свойств строками `k=v` (`formatProps`), пресет «delete» (без своих конфигов), чтобы не дублировать; `proposalId` |
| `resetOffsets` | `group` | `ResetOffsetsPanel` со стратегией и областью; `ResetPrefill` становится объединением прежнего вида (`{ topic, partition, offset }` из просмотра сообщений) и нового (`{ strategy, scope, proposalId }`); `timestampMs` переводится в значение `datetime-local` местного времени; `proposalId` |

- Над формой строка «Применяется предложение LLM: <заголовок>» (muted). Человек может править любое поле.
- Мутация формы передаёт `proposalId` (и для сброса — `request`) в команду; Rust ставит «применено» (§6);
  событие `health://changed` обновляет карточки.
- Стражи и `ConfirmDialog` без изменений: read-only блокирует, prod требует ввести имя подключения.
- Если вкладка объекта уже открыта, она активируется и получает новое заполнение; несохранённые правки редактора
  конфигов при этом заменяются (редактор предупреждает о несохранённых правках только при закрытии, как сейчас).

## 9. Хвосты G2 (первая задача плана)

Остатки финальной волны G2 (`.superpowers/sdd/g2-minor-ledger.md`, раздел «Final fix wave re-review»):

1. **Окружение проверки.** `CheckBar` помечает последнюю проверку, сделанную под другим окружением, чем текущее
   у подключения: «проверено как stage» (новый ключ `health.checkedAs`). `HealthService::latest_or_run`, присоединяясь
   к идущей проверке с другим окружением, дожидается её и запускает новую (один дополнительный цикл ожидания в пределах
   `check_wait`).
2. **Общее состояние «Проверка…».** Мутация проверки получает `mutationKey: ["healthCheck", connectionId]`; все
   `CheckBar` подключения читают `useIsMutating` и показывают «Проверка…» одновременно.
3. **Небезопасный id подключения.** Для id, не проходящего `safe_id` (импортированные подключения), имя файла в
   `health/` — `h-<sha256(id) в hex, 32 символа>.json`; удаление вместе с подключением — по тому же правилу; баннер
   обзора кластера больше не показывает ошибку «подключение не найдено».
4. **`cluster.noController`.** Запрос controller id повторяется один раз. Если контроллер неизвестен, но у всех
   партиций есть лидеры, находка — «предупреждение» с текстом про возможный таймаут запроса («Glafira could not learn the
   controller id in time; all partitions have leaders, so the cluster is probably healthy — repeat the check»);
   если есть партиции без лидера — «критично», как раньше. Параметры находки: `leaderless` (число партиций без лидера).
   Таблица §4 спеки G2 и тексты на 12 языках обновляются.
5. **Код `internal`.** Единое написание `internal` для файловых ошибок и паники фоновой задачи; тест закрепляет, что
   файловые ошибки сопоставляются по префиксам ключей `errors.io`, `errors.json`, `errors.storage.*`.
6. **Формулировки спеки G2** §2 (`rule_ids()` вместо `RULE_IDS`, сборка снимка в `collect.rs`,
   `describe_topic_configs` вместо `describe_configs_many`) и §3 (чувствительные значения отбрасываются по
   `isSensitive` и белому списку ключей в `kafka_source.rs`) приводятся к коду.

## 11. Ошибки

- Коды инструментов: `invalid_argument` (проверка §5, закрытое предложение при отзыве), `not_found` (группа,
  предложение), `not_allowed` (чужое предложение, подключение без доступа), `limit_reached`, коды Kafka из `ErrorCode`

## 13. Риски

| Риск | Мера |
|---|---|
| Prompt injection через имена объектов превращается в предложение изменения | Инструментов удаления и очистки нет; предложение — только файл Glafira; человек видит «было → станет» и подтверждает сам; стражи read-only и prod |
| Человек применяет, не глядя | Форма открывается заполненной, но не отправленной; обзор изменений и `ConfirmDialog` остаются; для prod — ввод имени |
| Расхождение предложения и кластера к моменту применения | Проверка при создании §5 и повторная проверка самой формой и Kafka при применении; срок 7 дней |
| Спам предложений | Лимит 50, обновление вместо дубля, «Удалить все предложения LLM», срок 7 дней |
| Ложное «применено» | Статус ставит только Rust после успеха операции; частичный сброс оффсетов не считается применённым |
| Рост файла `health/<id>.json` | Лимиты на размер текстов и списков, срок 7 дней |
